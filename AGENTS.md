# Architecture rules

- Resolve inbound WhatsApp contacts within the authenticated webhook's instance owner; create missing leads only when that owner's sales AI is enabled, so unsolicited contacts cannot cross accounts or populate inactive workspaces.
- Enforce owner-scoped sales AI phone exclusions at inbound receipt, model processing, and immediately before automatic sending; this also covers queued messages and configuration changes during generation.
- Keep sales AI attachments in private owner-scoped Storage with metadata in public.ia_anexos; select only active owner files on explicit requests and issue short-lived signed URLs for provider sends, never analyze uploads or accept model-generated file URLs.- Force sales AI escalation in code when the lead asks for a person or the reply promises a handoff; never rely only on the model flag, since it previously promised handoffs without escalating.
- Multi-user company environments (e.g. MiMo) use public.empresas + public.empresa_membros with roles checked by security-definer helpers (is_membro_empresa, tem_papel_empresa); company data must be scoped by empresa_id, never by personal user_id, and membership is granted only by a company administrator or server-side, never on signup.
- MiMo routes live under a client-only authenticated pathless layout and a membership-gated company layout; each server read independently checks the fixed existing company and active membership with the caller-scoped client, so route access never substitutes for data authorization.
- MiMo commercial leads and append-only change history live in separate company-scoped tables; database triggers normalize phones, validate lifecycle fields and audit writes atomically, while server functions recheck membership and use optimistic concurrency. Keep historical orders on reopen and never delete leads through the app, so reporting and duplicate prevention preserve legitimate history.
- MiMo WhatsApp ingestion uses an explicitly confirmed server-managed credential-hash/owner/instance binding and a service-only atomic RPC before legacy webhook dedupe; never auto-bind or copy personal leads. Transactional unique event IDs make retries safe without replaying personal IA, and commercial fields remain unchanged while company conversation events and contact timestamps are retained.
- MiMo Meta Ads CSV metrics are written only through an admin/gestor-checked security-definer RPC in one transaction, keyed by company+period+campaign+ad set+ad and replaced (never summed) on reimport, with identical files rejected by hash; Meta "leads" stay separate from CRM leads so ad-reported counts never inflate qualification or sales.
- The MiMo dashboard computes all indicators in one pure client-safe module from a lead cohort (entered in the period) and Meta rows fully inside the same period, served only to admin/gestor by a server function; this keeps numerators and denominators on the same period and makes the math unit-testable.
- MiMo weekly reports and CSV exports reuse the dashboard's pure cohort filters and are produced client-side only from rows an admin/gestor-checked server function returned; CSV cells are formula-neutralized and exclude phones/internal IDs, so reports never diverge from the dashboard or leak data.
- MiMo lead rows, lead history and WhatsApp events are readable in detail only by admin/gestor or the lead's assigned vendedor (RLS + pode_ver_mimo_lead); team-wide numbers for vendedores come only from the aggregate RPC mimo_indicadores_equipe, so colleagues' records never leak.
